## 1. 为什么不能当成小修

现有重制通知模块可复用规则鉴权、outbox、投递快照、幂等键、额度预占/结算、发送尝试、UNKNOWN 核实及本地验收工具。

但要恢复旧主业务，需新增“用户收到哪次变化”及“汇总投递具体包含哪些变化”的持久关系，调整已读/更替事务，设计成功后降级，再同步客户页面和管理统计。现有 DAILY 是按规则周期截取内容，不是未读变更汇总；直接改其含义会影响旧规则与验收。

工作跨数据模型、后端事务和事件、客户页面、后台口径、并发/恢复测试，不是几处函数或文案修改。实际工期由接手团队依据能力、最终通道和产品口径估算；不得把本单当作固定工期承诺。

## 3. SR-01：冻结业务规则及兼容方式

必须写清以下决定：

- 日常跟踪的触发源：新发布、修订、更替分别如何处理。
- 同一文章多次修订汇总展示最新一次还是多次；命中多个关键词如何计数。
- 已读只抑制确切版本或更新版本的变化，不能旧已读把新变化清掉。
- 移除当前更新、取消持续跟踪、及时降级三个动作分开。
- 即时是否一次性加急，更替成功后是否降回日常。
- 用户级时间是否首版限制 08:00/13:00/17:00；时区、静默和迟到补发窗口。
- 攻略禁止提醒、提前五分钟等是否仍需保留；它们是产品策略，不是行业硬规则。
- 日常已确认为企微客户联系群发任务方向；核实实际账号权限、客户绑定和员工执行结果，不混用内部应用消息的身份及回执。

推荐保留现有 AT_TIME 的预约用途，将旧式日常跟踪作为明确新语义接入。现有 DAILY/INSTANT 必须制定兼容策略：保留旧模式、显式转换，或只在全新上线时启用新模式；不能无说明地把数据库同一 mode 的含义改掉。

## 4. SR-02：增量模型与不变量

最高迁移已为 V20，下个编号执行时重新确认。不得修改 V1–V20。现有 V11 有 `mode IN('AT_TIME','DAILY','INSTANT')` 检查约束；新增模式时要在新迁移中调整，并同步 DTO 枚举。

需设计用户级设置、内容变更触发、命中来源、冻结批次成员等关系。具体表名由新工程领域决定，不复制旧 trigger 表。

必须覆盖以下不变量：

- 用户、文章和确切版本的事件消费有唯一性。
- 同一汇总成员不能同时属于两个可发送批次。
- 多个关键词命中来源保留，但用户看到的更新数按批准口径去重。
- 批次创建后新增变化不被该批发送结果清掉。
- 取消/已读/下线保留历史，不以删除历史投递来“恢复”额度。
- 既有 `notification_delivery`、尝试和额度账本继续可追踪。

## 5. SR-03～05：后端入口与事务

| 现有入口（新工程根目录相对路径） | 必要修改方向 |
| --- | --- |
| `backend/agri-modules/yunji-content/.../article/application/ArticleCommands.java` 的发布/replace/migrateSubscriptions | 发布和更替在同事务写明确事件；目标迁移与待变化引用一致；不新增授权额度 |
| `.../notification/application/NotificationService.java` 的 tick/enqueue/process/settle/reconcile | 分离事件规划、固定批次和发送处理；日常只汇总未处理变化；成功后降级幂等 |
| `.../engagement/application/EngagementService.java` 的 read | 更新版本已读并抑制可取消待发项；发送中/未知状态不能伪称已撤回 |
| `.../notification/api/NotificationController.java` | 新设置/待变化/移除/降级接口，鉴权/幂等/版本 DTO 完整 |
| `.../identity/application/IdentityService.java` 的 close | 注销后规则、触发和批次停止处理，会话作废且历史可审计 |
| `.../catalog/application/DiscoveryService.java` | 首页及待推送数量使用真实更新口径，不使用投递行数冒充 |

`...` 中的包根为 `src/main/java/com/sunshine/yunji/content`。修改前阅读完整调用图，避免形成 Engagement → Notification → Engagement 循环依赖。建议独立应用服务负责触发状态，不把所有逻辑继续堆进一个 NotificationService。

当前局部行锁/事务不能直接成为生产发送架构：外部网络请求不能长期放在持有数据库行锁的事务里。规划、领取租约、外部调用、回执结算分阶段；异常及租约恢复要与 UNKNOWN 语义一致。

## 6. SR-06：客户和管理端

客户入口：

- `apps/client/src/pages/notifications/index.vue`：双列表改为真正的日常待变化/即时待触发数据；展示可理解标题，不只实体编号。
- `notification-settings/index.vue`：全局时间/开关要实际读写，不只是说明页。
- `notification-edit/index.vue`：默认行为与新语义一致，保留明确的 AT_TIME 预约能力。
- `notification-status/index.vue`：真实授权/绑定提示；未接入显示待接入。
- `notification-history/index.vue`：区分批次、供应商接受和真正成功，不伪造送达。
- 资讯详情、关键词入口：保存后状态一致；授权拒绝保持原列表，不乐观假成功。

后台 `apps/admin/src/views/DeliveryCenter.vue` 的数量/样本上限、规则/批次/回执也需同步。API 契约、共享模型和对应页面注册按二次开发教程更新。

## 7. SR-07：真实平台接入交接

需要甲方提供：测试 AppID 与模板用途、企微应用/权限及消息类型、接收账号、合法 HTTPS API/回调域名。密钥通过受控配置传递，不写聊天或 Git。

平台实现必须包括身份映射、授权证据、额度、模板映射、签名与重放校验、外部请求超时、供应商回执、防重、失败分类和未知核实。不能以客户端 accept 直接增加正式额度。

本次已确认日常采用企微客户群发任务方向，任务由本系统自动创建，员工在企微侧执行。任务创建成功只是供应商接受，不能直接标 SENT；区分待执行、部分执行、已确认发送、失败与结果未知。核实可取得的结果查询/回执；无法确定时明确“已提交/待确认”。人工未执行不能导致下一时段重复建同一任务；自动提交和后台受控补提共用防重约束。具体批量发送能力和三个时段值仍待确认，不使用浏览器自动化模拟员工发送。

## 8. SR-08：验收与文档关闭

专项核查第 6 节的完整验收清单必须落为可执行场景。至少覆盖：无变更不发、命中去重、版本已读、当前更新移除、更替事件/成功降级、固定批次边界、授权拒绝、暂停/注销、内容下线、重试及 UNKNOWN、崩溃恢复与并发。

保留原测试 `notification_ops_suite.py` 的有用边界，不删断言冒充成功；改变旧语义需先修改版本化需求并注明转换原因。增加新 suite、真实页面与迁移升级演练。

文档同步范围：开发日志、当前阶段、强提醒使用规则、三端交接、二次开发教程、契约和验收要求。专项审计旧结论保留为历史，另附新实现证据，不直接把历史 findings 改成“无差异”。

验收完成必须给出具体提交和当前源码指纹；仅本地通过应写“本地业务通过、正式平台待验”。发布仍受 Linux、平台、安全和接收团队门禁约束。
