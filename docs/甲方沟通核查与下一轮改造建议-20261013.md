## 3. 需要纠正的技术推断

### 3.1 后台和小程序曾被混称

聊天已明确纠正“C 端等于管理端”的误解。因此，菜单和面包屑需求用于管理后台，不能直接套给小程序。

### 3.2 本机 cis4j 不等于一套已确认纯净且完整的前后端

本次在 `yangben/cis4j` 中没有找到 `package.json` 或 `.vue` 源码；存在基座 Java 控制器，同时也有 `agri-message` 等业务代码。因此，只能确认这份目录包含后端代码，不能据此声称拿到了未经业务修改的原版管理前端。

如后续取得真正原始前端，要核对版本、来源、许可证、依赖和身份接口，再决定是否只借鉴布局或复用经过确认的基座部分。不要从修改过的 `gld0.5` 整包搬回业务页。

### 3.3 菜单隐藏不代表接口关闭

框架功能是否占用磁盘很少，与权限和运行风险无关。代码生成、配置、缓存、租户、文件等能力须分别检查是否进入运行包、路由是否开放、服务端如何鉴权。生产不需要的开发工具应通过构建或配置禁用，不能只隐藏按钮。

“代码生成”一般指根据表结构和模板生成重复的 CRUD 代码，是开发辅助工具，不是客户业务接口。源码归档保留与生产可访问是两个决定。

### 3.4 强提醒不代表绕过微信或手机系统权限

应将“强提醒”当作产品名称，落实为授权范围内的订阅消息、企微任务及其状态管理。不能承诺强制弹窗、强制响铃或不受平台约束的无限发送。

材料中的“手机 App 获取权限后本地完成”也不是此项目的充分实现说明：是否本地调度、服务端推送或人工群发，需要根据具体平台和业务场景分别确定。

### 3.5 新材料缩小了企微第一阶段目标，但没有消除后端业务缺口

旧 `DailyRemindServiceImpl.java` 在 `addMsgTemplate` 返回 `errcode=0` 后立即标记触发项已推送。该实现混淆了任务提交与真实发送证据，不可直接继承。

对方明确接受“后台建任务、手机执行”，这可以作为较小的首阶段目标。用户级未读汇总、去重、已读抑制、失败恢复和身份映射仍需实现。即时微信订阅消息是另一条链路，不能被企微手动发送替代。

## 4. 推荐的工程方案

### 4.1 使用现有新后台，重做导航和业务工作区

建议顶层分组：

1. 内容管理：资讯、通知、更替、板块标签关键词。
2. 活动与下载：活动内容、展示位、报名、资料、插件及教程。
3. 客户管理：客户列表、关注与提醒明细、反馈。
4. 强提醒管理：每日设置、即时设置、模板、发送任务、推送记录、统计。
5. 数据统计：内容、访问行为和用户概况。
6. 系统管理：工作人员、权限、字典、参数、日志、经过验证的监控能力。

当前路由尽量保持兼容；新旧入口有明确重定向。常用操作使用专用页面，通用表单仅承担简单字典维护。界面错误、空列表、无权限、未配置、尚未接入必须区别展示。

### 4.2 板块→标签→关键词：统一操作，保持概念独立

现有关键词是全局规范词；同一个词可以用于多个场景。推荐在板块/标签树下维护“关键词编排关联”，保留关键词统一 ID、别名和治理记录，不为每个标签复制一套关键词实体。

显式运营关联与从文章推导出的关联应分开，不能悄悄把当前接口语义改掉。增加关系迁移、新接口及旧接口兼容处理；文章的关键词命中、用户订阅和分类展示分别定义规则。

首版建议：标签属于一个板块，父标签必须同板块；关键词允许关联多个标签；删除引用采取受限删除或停用；父节点关注是否包含子节点沿用当前“精确匹配”，需要改变时另记需求，不由树形 UI 自动改变业务。

### 4.3 强提醒使用新业务核心和窄接口适配器

优先方案是重新实现最小企微适配器，放在独立模块/包内。核心负责触发、批次、权限与账本；适配器只负责身份映射后的平台请求、任务查询和结果转换。

建议接口能力为“创建群发任务、查询任务执行结果”，使用固定批次编号和幂等请求标识。适配器不能直接修改文章、用户和提醒业务表。

预期状态至少区分：待提交、平台已接受/待员工执行、部分执行、已确认发送、失败、结果待核实。是否有可靠的送达/阅读证据以平台真实提供的字段为准；不能将无回执解释为成功。超时未知先核实，避免盲目重建群发任务。

根据同日补充答复，日常任务由调度自动冻结收件人与内容并提交企微，无需工作人员在本系统再逐批点击创建。后台提供预览、总开关、异常核实和受控补提；人工发送发生在企微侧。补提与自动提交共用防重约束。运营不能代替用户授予微信订阅授权。

无需仅为“专业性”拆成多服务；窄接口模块即可先实现。确需临时旧实现时，备选是独立进程/容器、独立账号和配置、最小网络权限、独立数据，不共享主业务数据库写权限；通过合同接口和总开关接入，并明确移除条件。此备选仍有部署与维护成本，不保证比重写薄适配器更快。

材料中关于复用的讨论不视为本轮已开始移植。当前建议仍为按功能重写最小适配器；不复制旧 demo 的业务代码和表结构。

## 8. 甲方补充答复：已确认的业务边界

来源：2026-10-13 用户转述的最新甲方答复。以下是业务意图确认，不是平台功能或现有代码的运行验收。

### 8.1 管理端来源

原始管理端前端文件已丢失；当前可研究的是 `yangben/gld0.5`。此前“公司继承的管理员后端”指 cis4j 的账号、角色、部门、权限等后端接口，不代表本地另有完整的原版管理前端。

下一轮可从 gld0.5 核对基座菜单、页面及接口映射，形成来源清单。不能仅凭外观或代码风格判断哪段属于原版：需要可核对的上游版本、许可证和差异证据。来源无法证明时，按功能重写页面；公司基座接口继续沿用，旧业务逻辑和表结构不搬回。对方说“好分辨”不能替代来源审查。

### 8.2 日常提醒：自动创建任务，人工执行发送

确认流程：用户建立企微联系关系 → 本系统整理其待推送更新 → 本系统调用企微接口创建任务 → 工作人员在企微侧的三个固定时间点执行发送 → 本系统依据可取得的平台结果更新记录。

本系统负责定时准备、去重、固定批次、任务创建、防重、失败处理及状态核实；人工执行属于业务流程本身，不是要求在新后台补一个自动点击企微界面的程序。不会通过模拟登录或界面自动化绕过该环节。

“用户关注企微”是业务俗称，实施时须核实客户联系关系及其与本系统用户的绑定。小程序身份、unionid 和企微 external_userid 不能混用；具体身份字段和绑定方式由实际平台权限确认。

待员工执行的任务保持在途状态，不因跨过下一时段就重复创建相同内容。后续新变化另行归批。任务已经提交后发生已读，不能只更新本地状态就宣称外部任务已撤回；需按平台可用能力和真实结果处理。

“全选、一键推送”是对方描述的操作期望，其界面、任务粒度、发送限制和批量能力待测试企业验证，不视为已经证实的平台保证。

### 8.3 即时提醒：一次性订阅授权后自动调用微信接口
