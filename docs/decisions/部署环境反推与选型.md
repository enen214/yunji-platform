# 部署环境反推与选型

2026-10-04，依据用户要求自主反推。旧数据不迁移，先做本地完整验证，无微信/企微平台资源。仅研究笔记和公司框架用于判断技术约束；旧demo代码、表、前端和部署脚本不进入新实现。

| 事实或决定 | 依据 | 可信边界 |
| --- | --- | --- |
| 服务需要Java、MySQL、Redis | 研究笔记 `yangben/项目总结与决策记录.md`；新工程POM与application.yml | 直接可验证的技术约束 |
| 管理端是静态Vue产物，C端是uni-app微信小程序/H5 | 新工程apps/admin与apps/client构建 | 小程序编译不能代替平台发布 |
| 原部署OS、机器配置和Docker条件不明 | 笔记没有足够证据 | 不能声称反推出原公司实际主机 |
| 新部署选Linux LTS、JDK21、MySQL8、Redis7、Nginx | 为依赖和运维独立作出的设计决策 | Java字节码target17，运行选21；需目标机验证 |
| 单校平台默认公共租户000000 | 当前业务约束 | 不宣称多租户SaaS已验收 |
| 同源HTTPS，API原路径 `/api/v1` | 新契约和客户端 | 不继承旧 `/prod-api` 或旧域名 |
| Windows本地隔离运行 | 当前机器Java/MySQL/Redis/Node/Python均可用 | 本地没有Docker，Linux容器未实测 |

采用原生systemd主方案：不用Docker即可部署，避免从未知历史环境引入额外条件。数据库、Redis、附件与应用发布目录分离；应用仅有DML，迁移工具独立账号，附件永不映射Nginx静态目录。备份停写，恢复到新库新目录，保留原库可追溯。

旧笔记里的域名、密码、库名和端口只记录为历史事实，不能进入新生产配置。未知的最终域名、TLS证书、资源规格、可用微信AppID和企微应用等保留为接收团队接入项；不用它们阻止本地合成验收。

可执行配置和步骤位于 `deploy/`；验证结果以 `reports/operations.json` 为准。当前仅原生Windows等价应用与数据库流程可实测，Linux上线前另有目标机验证。
