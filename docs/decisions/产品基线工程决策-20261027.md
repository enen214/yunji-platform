# 产品基线工程决策

2026-10-27；状态：用户授权自主设计后的研发默认方案，尚未全部实现或验收。后续确有证据需调整时记录新决策，不能悄悄变更验收语义。

| 编号 | 采用的规则 | 理由/边界 |
|---|---|---|
| PB-01 | 保存即发布，不做内容审核和业务内容版本；错字原地改，大改另建资讯 | 满足简化运营。保留并发锁、审计、评审快照、文件版本和迁移版本 |
| PB-02 | 资讯只能一个板块，至少一个所属标签、至少一个全局关键词 | 分类专门规则优先于可选字段列表中的冲突文字 |
| PB-03 | 更替使旧文结束，旧详情仍可读；下线/删除不再公开 | 生命周期与编辑状态分开；更替操作不再把旧文等同下线 |
| PB-04 | 业务时区 Asia/Shanghai，持久化时间使用 UTC | “当日”按业务时区截断。导入无时区时间按该时区解释，回执写明 |
| PB-05 | 普通排序为基础分×关注系数×曝光系数，稳定并列键为发布时间、ID | 不靠任意加大置顶权重实现特殊优先级；过滤先于排序 |
| PB-06 | 基础分=10×重要度+5×剩余热点天数+时效分，时效分上限50 | 重要度1～5、热点0～30。关注0/1/多条命中系数为1/1.5/2，零曝光系数1 |
| PB-07 | 时效分采用50×2^(-年龄/半衰期) | 紧急6h、短期24h、长期7d从发布时间起算；定时类生效前保持50，生效后从生效时间起按48h半衰。年龄截断非负；急迫性若另加只能作新决策 |
| PB-08 | hotDays 按业务时区自然日计算，到期边界排除；0不进入首页/板块列表 | 列表分数用0～30剩余天数；后台提示可见入口，演示样例必须含非零热点 |
| PB-09 | 首页顺序：运营强加、紧急、置顶、普通；所有条目服从生命周期、筛选和热点门槛 | 强加只决定首页前置；不绕热点和安全过滤；置顶按原规则豁免已读/曝光。强加若同时置顶才获此豁免 |
| PB-10 | 点详情成功加载后记已读；失败不记。首页/盒子已读排除，置顶例外 | 搜索/收藏/历史保留可读资讯的访问，不把“永久不出推荐”理解成永久打不开 |
| PB-11 | 曝光以真实滚动进入可视区计数，30秒服务端去重，全局累计、另有业务日计数 | 初始仅渲染不报曝光；程序定位不伪造手势滚动。先曝光后点击不回减，点击改显式已读；累计9次为隐式已读，当日3次当天冷却 |
| PB-12 | 关注对象仅资讯、关键词、标签；关注不自动强提醒；设提醒成功自动关注 | 即时授权失败不能遗留“已设置成功”；取消关注提供是否停提醒选择 |
| PB-13 | 盒子跨栏按更替>关注更新>推送去重；默认平铺，可选小盒子 | 同栏多标签小盒子允许重复展示，但曝光、已读、取消待提醒共享用户资讯状态 |
| PB-14 | 搜索会话冻结顺序，逐次读取仍校验撤回；服务端有界续期清理 | 不无界永久保存，不展示刷新提示，不能借快照绕过下线/删除 |
| PB-15 | 热词按近7天去重搜索人数；信息热度按近7天点击量；不做停留时长/搜索点击率 | 原始日志保留无结果分析；热词20、历史20、热搜信息默认10条，可配置5～10 |
| PB-16 | JSON 文件与粘贴共用单条命令；板块/标签按名查已有；关键词全局规范化复用 | 三类内容校验一致，不通过导入绕过必填；规范化方案与词条管理一致并有唯一约束 |
| PB-17 | 导入预检500条、5MiB；行级事务允许部分成功；60秒为性能目标/超时治理 | 不能把已提交条目说成整批未入库；批次结果可恢复查询，失败说明带原序号 |
| PB-18 | 同请求幂等、不同请求允许有意重复内容；回执分createdKeywords和duplicatedKeywords（新建与复用） | 不按标题覆盖或相似度去重。同幂等键不同内容冲突，同内容返回已有结果 |
| PB-19 | 成功批次条目统一检测更替，只对批次开始前的有效旧文，排除本批互比 | 用批次边界、候选唯一约束和补偿防重复/漏执行；不承诺候选数量必定≤导入条数 |
| PB-20 | 用户看提醒配置不看投递账，后台保留授权、预留、发送尝试、错误和告警 | 微信一次授权一次发送。界面不讲额度不等于无授权限制，企微仍需员工操作 |
| PB-21 | 日常三个时段由配置给出，T-5min建任务；不擅自承诺企微任务可撤单个收件人或自动发送 | 先核对现有时段；没有正式值时仅本地夹具使用明确标识的样例。取消能力按真实API实测记载 |
| PB-22 | 文件采用存储提供者适配，生产微信云存储，后端签发临时链接不发fileID | 无资源时用明确本地测试提供者，生产不静默降级；统计区分签发与下载完成，不编造完成量 |
| PB-23 | 活动引用全局文件版本与评审项目，C端本期无独立评审/资源/插件页 | 新专门活动页面仍需小程序开发发布；不提前实现后续的插件平台/动态路由系统 |
| PB-24 | 单运营角色、菜单存库后端下发；统一员工入口保护加业务对象权限 | 没有权限注解不等于没有鉴权；员工与客户隔离，不盲拆公司基座账号体系 |
| PB-25 | 干净安装给schema/seed，升级保留版本与校验；初始凭据部署注入或生成 | 不迁旧业务数据、不污染生产seed；保留升级和恢复能力，不承诺Windows成功等于Linux验收 |
| PB-26 | 旧验收不计入新基线通过率，真实平台与目标环境单独门禁 | 新报告必须带输入、源码指纹和场景；只完成构建不能写本地功能全验收 |

以上是默认研发决策，不是所有对应能力已实现的完成清单。涉及平台实际能力的条目保留待实测状态。

## PB-27～PB-32：实施后的明确差异

- PB-27：退役接口应HTTP404；修复公司框架Spring6静态资源异常被HTTP200包装的缺陷。评审历史按提交版本排序，再按决定时间/ID，避免随机ID在同秒内打乱补正历史。
- PB-28：客户持有客户token调用STAFF接口仍返回401，规格12-03写403；已拒绝访问，状态码差异明确保留。若统一改403，需连同框架登录、前端会话和负例一起迁移。
- PB-29：不迁旧业务库，不等于删除授权框架和新工程所有历史表。保留稳定外键、迁移史、评审快照、文件版本；13-02“彻底新表”没有照做，退役模型仅关HTTP/路由并保留历史结构。
- PB-30：协议同意记录写路由取消，协议正文历史表保留；头像字段只读展示，选择上传未完成。活动承载模板不冒充每活动专门设计。
- PB-31：微信云适配协议已实现但真实联调未验，当前仍落本地副本；真实提醒Worker无发送器接线。二者是明确的交付缺口，不仅是外部凭据阻塞。
- PB-32：234条逐条采用有界状态：局部场景通过、实现存在未验、部分、后续、待议、外部待验、已定。可推送候选仅核对选定本地回归与披露完整性；绝不由此生成生产PASS。
