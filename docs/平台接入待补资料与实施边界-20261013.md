# 平台接入待补资料与实施边界

本轮尽可能完成本地可重复验收的业务工作。以下资料决定真实身份与消息协议的接法，不由旧 demo 猜测；不向开发方索要生产服务器管理员权限等与研发无关内容。密钥只放环境变量或未入库配置，勿贴聊天和文档。

## 研发需要的最小资料

| 项目 | 提供内容 | 开发用途 |
| --- | --- | --- |
| 小程序测试身份 | 独立测试 AppID、可登录的测试用户、配置权限联系人 | 核验 code2session 和已加密身份的 AppID 隔离，不复用本地合成用户 |
| 订阅消息 | 已审核一次性模板 ID、字段名/类型、提醒用途、跳转页面要求 | 完成字段映射、字符串限制、一次性许可和后台发送接线 |
| 平台消息事件 | 可访问的 HTTPS 测试域名、平台当前支持的事件/回调配置及测试权限 | 确认如何形成可验证授权记录，签名/解密/去重/重放拒绝；前端 accept 不直接铸造永久额度 |
| 企业微信 | CorpID、客户联系相关权限、测试发送员工与外部联系客户、可建任务的应用/账号配置 | 确认客户联系群发能用，不误接内部 application message/send |
| 客户绑定 | 小程序客户怎样识别到准确 external_userid 的经确认流程 | 用户登录身份与企业客户 ID 属不同体系；扫码状态/事件关联或受控核实绑定需依据可用平台能力实施 |
| 任务结果 | 员工测试帐号和有代表性的创建/执行/部分失败查询结果 | 绑定 msgid、分页拉取执行状态，完成内部批次归并，不把建任务成功写成送达 |
| 产品口径 | 三个具体时段；是否接受“下一次即时，成功后日常”；关键词仅新文章首次发布触发 | 确认本轮默认设计是否符合对方业务，无须为了示例“6点”硬编码 |

目前已确认 Linux x86_64/amd64 和 Docker，不重复询问。主机公网备案、生产域名证书管理、告警值班和生产运维组织由部署团队负责；研发只在接入/复验需要时取相应测试入口。

## 接线顺序和验收

1. 保持现有真实发送关闭。记录测试 AppID/CorpID 与用途，密钥注入到独立测试配置。
2. 完成真实身份和用户意愿/授权证据链，查明撤销、重复事件、过期与 AppID 不匹配的处理。加密身份读取不得出现在日志或公开 DTO。
3. 按明确模板构造即时消息；日常按冻结批次构造企微客户联系任务，并保存准确的目标身份与 msgid 关联。
4. 接到 ReminderWorker 的事务外发送段，不能在发布事务持锁时调网络。只有明确未发送的失败可补提；超时结果未知冻结待核实。
5. 平台任务创建后保持 AWAITING_STAFF，按完整分页结果处理未执行/部分/执行失败/确认完成。工作人员的企微操作不由本系统伪造。
6. 用独立测试用户验收正常发送、解绑、无授权、额度用尽、超时、重复回执、分页、部分结果、进程重启及并发，形成与实际源码一致的报告。
7. 再开启正式能力指示，更新 C 端授权、生产调度和模板管理说明；不能只把 realProviderReady 改成 true。

这些步骤包含平台相关开发与真实联调。目前资源不足时，预先写一个永远返回成功的供应商会掩盖业务缺口，所以交接中明确保留。已有 ProviderHttpTransport / ProviderProtocol / WecomTaskTransport 是可测试的底层能力，不等于上述接线完成。
