# 全模块字段与一致性设计

状态：实施规格。V1–V4 已提供并运行核心 DDL；下列补充字段/表还需在对应功能首次开发前写成 V5 起的迁移并验证，不将文档当作已建表或已实现业务。

## 通用决策

内部 ID 为全局唯一 BIGINT，对外字符串；运营对象含 tenant_id、created_by、created_at、updated_at、lock_version、deleted_at。时间用 UTC；对象关联必须同时验证租户。当前 V4 外键验证对象存在、版本归属，不能阻止所有跨租户误关联，所以用例必须做相同租户授权查询；多租户上线前再增加复合 FK。单租户首期固定 000000，多学校用组织维度实现。

目录软删除仍占用业务唯一名，恢复原 ID，不静默重建同名实体。关系索引是已发布版本的可重建投影，更新时同事务删旧/插新，不对每条关系加 soft-delete 字段。草稿关系只在不可变版本快照中；公开查询不读草稿快照。

## 内容与审核状态分离（S3 必做迁移）

|对象|新增/明确字段|约束与职责|
|---|---|---|
|article|publication_status(DRAFT/PUBLISHED/OFFLINE)、submitted_version_id、lock_version|公开可见性属于发布状态；编辑状态不可覆盖它。现有 status 在 S3 收敛为发布状态，不能另建平行内容表|
|article_version|review_state(DRAFT/SUBMITTED/APPROVED/REJECTED/WITHDRAWN)、submitted_at、decided_at|正文、来源、分类组织关键词快照不可变；仅审核元数据可按状态机变更|
|article_review|version_id、action、operator_id、request_id、comment|审核绑定具体版本，审核/发布/撤回都有记录；APPROVE 不是直接改变公开指针|
|user_read_state|read_version_id|明确读过哪个发布版本；内容更新未读不依赖曝光次数；FK须校验article与版本归属|

示例：V1 已发布；生成 V2 草稿→提交→审核时，article.current_version_id 始终为 V1，公开查询继续返回 V1。发布 V2 才在同事务改公开投影、三组关系、current_version_id、审计和 outbox。退回 V2 不影响 V1。必须用 expected lock version + exact versionId 防止“审V2发V3”。

已有 ArticleLifecycle 是首次发布的领域示例，**不得直接作为已发布修订工作流**。S3 用版本审核状态机替换其应用层调用；旧样例不提供编辑已发布内容的能力。

## 身份与目录补充

|表|主要字段|关键约束|
|---|---|---|
|user_consent|user_id、page_version_id、consent_type、accepted_at、client_id|协议同意绑定不可变正文版本；一用户一版本一类型唯一|
|content_page_version|page_id、version_no、title、content、published_at|发布正文不可变；协议覆盖写必须改为版本化|
|keyword_alias|tenant_id、normalized_alias、keyword_id|租户内规范别名唯一，不能形成别名到别名循环|
|study_subject|tenant_id、organization_id、code、name、status|学校内科目代码唯一，组织FK|
|study_dimension|tenant_id、kind(GRADE/MAJOR)、code、name、status|kind+code唯一；画像及资格引用稳定ID|
|subscription_box_preference|user_id、follow_id、hidden、updated_at|user+follow唯一，只影响UI显示，不改变订阅和提醒|
|filter_subscription（候选）|user_id、category_id、organization_id、filter_hash|规范化组合hash唯一；候选在业务确认前不扩大 user_follow 多态类型|

外部身份 app_id+provider+subject_hash 唯一；HMAC key_version 需要入库以支持轮换。手机号绑定是候选，平台解码或验证码流一并冻结后开发，不从 demo 绑定方式推断。

## 强提醒（S5）

现有 notification_rule/delivery 是起点字段，不足以支持完整提醒。S5 对同名表新增字段，禁止创建第二套 remind/biz_notify 主链。

|表|字段|约束和查询|
|---|---|---|
|notification_rule|user_id、target_type、target_id、mode(AT_TIME/DAILY/INSTANT)、channel、timezone、scheduled_at、local_send_time、quiet_start/end、enabled、lock_version|相同规范规则hash唯一；目标存在/可见；本人查询；索引user+enabled、enabled+scheduled_at|
|notification_delivery|rule_id、rule_version、dedupe_key、user_id、article_id、article_version_id、channel、status、next_attempt_at、lease_until、provider_message_id、attempts|dedupe_key唯一；claim到期行后校验rule_version/取消状态；索引status+next_attempt_at|
|notification_attempt|delivery_id、attempt_no、request_hash、outcome、provider_code、started_at、finished_at|delivery+attempt_no唯一；不保存明文身份、token、正文中的私人信息|
|notification_quota|user_id、app_id、channel、template_key、available、reserved、consumed、lock_version|维度组合唯一，计数非负；微信授权accept不能凭空增加永久额度|
|notification_quota_ledger|quota_id、delivery_id、operation(RESERVE/COMMIT/RELEASE)、amount、created_at|delivery+operation唯一，所有计数和账本同事务|
|notification_binding|user_id、provider、app_id、encrypted_subject、binding_state、key_version|平台subject_hash唯一；只返回绑定状态|
|notification_callback_receipt|provider、callback_key、payload_hash、handled_at|provider+callback_key唯一；验签后处理；重复内容不再扣额度|

流程：发布outbox→收据去重→建立delivery→原子预留→发送→成功结算/明确永久失败释放/可重试退避/UNKNOWN冻结。lease只控制工作者，数据库账本才是额度真源。供应商不支持幂等时不承诺exactly-once；UNKNOWN不得立即释放并重发。

## 文件基础（S4 前置，评审/资料共用）

|表|字段|约束和职责|
|---|---|---|
|file_object|id、tenant_id、owner_realm/id、storage_provider、object_key、sha256、size_bytes、media_type、privacy(PUBLIC/PRIVATE)、status(UPLOADED/VERIFIED/REJECTED/DELETED)、created_at|provider+object_key唯一；只存对象键，不能将持久签名URL入库；校验实际文件类型/大小|
|file_reference|file_id、owner_type、owner_id、reference_version_id|明确引用账本，复合键唯一；清理只对无引用且过保护期对象|
|download_ticket|ticket_id、file_id、principal_id、expires_at、nonce_hash、status、issued_at|不可猜随机票据；授权检查在发票据与取文件时都执行；签名仅短时|
|download_event|ticket_id、event_type(ISSUED/PROVEN_COMPLETED)、received_at、evidence_source|票据发放≠下载完成；客户端自报不是服务端完整下载证据|

私有材料不开放静态目录。下载需通过有授权的服务端代理或对象存储短时票据。公开图也要校验MIME；禁止任意URL抓取形成SSRF。

## 活动（S6）

|表|字段|约束和职责|
|---|---|---|
|activity|tenant_id、article_id、organization_id、registration_start/end、event_start/end、capacity、confirmed_count、waitlist_enabled、status、lock_version|article_id可唯一关联活动展示；capacity及计数非负且confirmed_count≤capacity；窗口结束晚于开始|
|activity_form_version|activity_id、version_no、schema_json、created_at|activity+version唯一；schema仅允许已支持的字段类型及长度，不执行客户端脚本|
|activity_registration|activity_id、user_id、form_version_id、answer_snapshot、status、queue_seq、submitted_at、cancelled_at、lock_version|activity+user唯一；状态明确；答案快照与表单同版本；索引activity+status+queue_seq|

报名同事务：锁/条件UPDATE活动容量→幂等写报名→审计/outbox。重复报名应先返回已有状态，不能先扣名额。取消与候补推进采用同一容量锁，严格冻结候补顺序（submitted_at/id）。

## 学生评审申报（S7）

|表|字段|约束和职责|
|---|---|---|
|review_campaign|tenant_id、organization_id、article_id、open_at、close_at、rule_version、status|公开简介可关联资讯，申报材料永远私有|
|review_requirement|campaign_id、rule_version、requirement_key、required、file_type_allowlist、max_size、eligibility_json|campaign+version+key唯一；条件是声明式白名单，不执行任意表达式|
|review_application|campaign_id、user_id、status、current_submission_id、latest_submission_id、lock_version|campaign+user唯一；用户只能改草稿/补正版本|
|review_submission|application_id、version_no、requirement_snapshot、eligibility_snapshot、submitted_at|application+version唯一；材料/资格快照提交后不可改|
|review_submission_file|submission_id、requirement_key、file_id|submission+key唯一；file归属和privacy须校验|
|review_decision|application_id、submission_id、decision、comment、reviewer_id、decided_at|提交版本归属复合约束；评审范围按组织查询|

窗口外提交拒绝，提交前一次校验全部必需材料和已验证文件。补正建新版本，旧审意见不能覆盖新材料。评审人与内容审核服务是不同用例，禁止一个万能ReviewService。

|---|---|---|

## 运营、行为和报表（S4/S9）

behavior_event 新增 client_event_id、ingested_at、server_principal_id；会话主体来自服务端，客户端不能指定可信userId。幂等以principal+client_event_id，参数上限/事件白名单/时间漂移限制冻结后实施。

analytics_daily 用 tenant_id+date+metric_key+dimension_hash 唯一，来源是可重跑事件聚合；跨午夜要有固定时区。UV统计须定义去重粒度。报表不从用户隐私表直接联表返回明文身份。

Banner/推荐位复用运营表，目标类别必须白名单并验证关联可见性；协议页走content_page_version，禁止覆盖用户已同意的正文。关键词黑名单追加治理状态/表，不删除历史词关系。

## 数据迁移是另一个项目步骤

默认不迁真实数据。确需移交时，在staging中保留原始行、来源表和hash；映射→校验→合成演练→审核发布，错误行隔离，不隐式选sub_message或info为权威。migration_id_map存旧到新ID映射，重跑同批幂等。用户身份迁移需要平台AppID归属证据，不根据同昵称合并。
