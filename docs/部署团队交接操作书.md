## 0. 不可违反的边界

- 只部署本重制仓库和交付包里的 `source`、`artifacts`、`deploy`、`scripts`；不要复制 `yangben`、旧 demo 的 Java/Vue/uni-app、旧 SQL、旧配置、旧附件目录或旧部署脚本。
- 试验环境使用全新数据库和全新附件目录；不连接旧库，不导入 `database/fixtures`，不迁移旧数据。旧数据迁移是另一个需批准、可回滚、可审计的项目。
- `local` profile、`/api/local/*` 和 `/api/v1/auth/customer/local` 只允许开发工作台在回环使用，不能出现在服务器公网或生产配置中。
- 服务器不需要 Node.js 或 Maven 来运行已构建包；它需要 Java、Python、MySQL 客户端、Redis 和 Nginx。若必须在服务器重建，需另行审查构建机和依赖，不得直接覆盖当前 release。
- 生产凭据只放受限文件或密钥系统，不进 Git、不发聊天、不写命令参数。身份 HMAC、身份加密、token secret 跨重启保持不变。

## 2. 接收前清点

从 GitHub 拉取的是源码、模板、文档和报告，不是可直接运行的服务器安装包。构建人员按 [本地开发与验收使用说明](本地开发与验收使用说明.md) 安装依赖、构建，使用 `delivery_bundle.py` 生成新的交付 ZIP；不要使用较早 ZIP 代替当前分支。打包脚本已经包含核心、扩展、闭环浏览器报告和需求追踪报告；签收时逐项比对门禁 `evidence` 中的证据与同一提交，不修改已签收 ZIP 内的 manifest。

在受控终端保存交付包，不要解压到旧工程目录。ZIP 内没有同名外层目录，展开后直接为：

```text
<本次新建解压目录>/
  source/       # 源码、迁移、脚本、部署模板、契约、报告、文档
  artifacts/    # backend/agri-admin.jar、admin、client-h5、client-mp-weixin
  manifest.json # 每个文件 SHA256、范围和排除项
  先读我.md
yunji-development-<UTC>.zip
```

校验压缩包和 manifest 后再安装。PowerShell 示例：

```powershell
Get-FileHash '.\yunji-development-<UTC>.zip' -Algorithm SHA256
if (Test-Path .\yunji-unpacked) { throw '请使用新的解压目录' }
Expand-Archive '.\yunji-development-<UTC>.zip' .\yunji-unpacked
Set-Location .\yunji-unpacked
```

Linux 侧：

```bash
sha256sum 'yunji-development-<UTC>.zip'
mkdir '/srv/yunji-incoming-<UTC>'  # 必须新建；存在则停止
unzip -q 'yunji-development-<UTC>.zip' -d '/srv/yunji-incoming-<UTC>'
cd '/srv/yunji-incoming-<UTC>'
```

将下面完整代码保存为解压根目录的 `verify-manifest.py`，Windows 运行 `python verify-manifest.py`，Linux 运行 `python3 verify-manifest.py`。它比对 manifest **已记录**的大小和哈希，不是重新生成一份哈希再自验：

```python
import hashlib
import json
from pathlib import Path

root = Path.cwd().resolve()
manifest = json.loads((root / 'manifest.json').read_text(encoding='utf-8'))
assert manifest['files'], 'manifest 没有文件'
seen = set()
for row in manifest['files']:
    rel = Path(row['path'])
    assert not rel.is_absolute() and '..' not in rel.parts, f'非法路径: {rel}'
    assert row['path'] not in seen, f'重复路径: {rel}'
    seen.add(row['path'])
    raw = root / rel
    for part in (raw, *raw.parents):
        if part == root:
            break
        assert not part.is_symlink(), f'拒绝符号链接: {part}'
    path = raw.resolve()
    assert path.is_relative_to(root) and path.is_file(), f'越界或缺失: {rel}'
    assert path.stat().st_size == row['bytes'], f'大小不符: {rel}'
    assert hashlib.sha256(path.read_bytes()).hexdigest() == row['sha256'], f'哈希不符: {rel}'
print(f"校验通过: {len(seen)} 个文件")
```

使用普通解释模式执行，不加 `-O`（上述代码用断言校验）。manifest 不是签名凭证，仍需独立比较研发提供的 ZIP SHA256。Python 要求 3.10+。

如果 ZIP、manifest、源码指纹或报告时间不一致，停止交接，要求研发重新生成包。不要使用服务器上手工改过的文件作为最终版本。交付包明确排除 `yangben`、`.runtime`、依赖缓存、密钥、备份和旧数据。

## 3. 目标主机和网络准入

建议先用隔离主机，不直接切旧站域名。至少准备 Linux LTS、4 vCPU/8 GB RAM/100 GB SSD 的起始规格（不是容量承诺），JDK 21、MySQL 8、Redis 7、Nginx、Python 3.10+、`mysql`/`mysqldump` 客户端、NTP 和可用 TLS 证书。设置主机时区用于日志显示，数据库和应用时间按 UTC 保存。

只开放 80/443；MySQL 3306、Redis 6379、API 18088 只监听回环或私网安全组。准备 DNS、HTTPS 证书、证书续期方式和防火墙审计。小程序请求的 API 域名必须是微信认可的 HTTPS 合法域名，不能填 `127.0.0.1` 或 HTTP。

以下服务器命令由系统管理员在受控终端执行。需要读取 0600 的迁移配置和创建 `/opt` 下的运维 venv 时，使用授权的 root shell（例如 `sudo -i`）；运行服务仍使用无登录权限的 `yunji` 账号。创建专用账号和目录：

```bash
sudo useradd --system --home /var/lib/yunji --shell /usr/sbin/nologin yunji
sudo install -d -o root -g yunji -m 0755 /opt/yunji/releases
sudo install -d -o root -g yunji -m 0755 /opt/yunji
sudo install -d -o yunji -g yunji -m 0700 /var/lib/yunji/files
sudo install -d -o root -g yunji -m 0750 /etc/yunji /etc/yunji/tls
sudo install -d -o yunji -g yunji -m 0750 /var/log/yunji
```

发布目录按 `/opt/yunji/releases/<版本>` 保存不可变包，`/opt/yunji/current` 指向当前 release。配置、私有附件、数据库和 Redis 数据不放在 release 内。

## 4. 凭据和数据库初始化

由 DBA 在受控终端创建新库账号。迁移账号只用于迁移/备份，应用账号只用于运行时目标库；不要把迁移账号写入 API 配置。下面是权限意图，具体语法按公司 MySQL 安全规范执行：

```sql
CREATE USER 'yunji_migrator'@'127.0.0.1' IDENTIFIED BY '<随机迁移口令>';
CREATE USER 'yunji_app'@'127.0.0.1' IDENTIFIED BY '<随机应用口令>';
-- 推荐由 DBA 先 CREATE DATABASE yunji，再授予下面的目标库权限；随后使用 migrate。
GRANT CREATE, ALTER, DROP, INDEX, CREATE VIEW, CREATE ROUTINE, ALTER ROUTINE,
      REFERENCES, SELECT, INSERT, UPDATE, DELETE, EXECUTE
      ON `yunji`.* TO 'yunji_migrator'@'127.0.0.1';
GRANT SELECT, INSERT, UPDATE, DELETE ON `yunji`.* TO 'yunji_app'@'127.0.0.1';
```

推荐由 DBA 创建带 `utf8mb4` 的空库并授予上述目标库权限，然后使用 `migrate`；若组织要求由工具创建库，则 DBA 可临时授予迁移账号全局 `CREATE`，仅执行一次 `initialize` 后立即收回该全局权限。不要用 `framework-schema.sql` 手工绕过工具。将 `source/deploy/migration.env.example` 复制为 `/etc/yunji/migration.env`，权限 0600，填写主机、端口、数据库、迁移账号、口令和 `YUNJI_MYSQL_BIN`。执行：

```bash
sudo chmod 0600 /etc/yunji/migration.env
python3 -m venv /opt/yunji/ops-venv
/opt/yunji/ops-venv/bin/python -m pip install -r source/scripts/requirements.txt
. /opt/yunji/ops-venv/bin/activate
set -a; . /etc/yunji/migration.env; set +a
/opt/yunji/ops-venv/bin/python source/scripts/database_ops.py migrate   # DBA 已预创建空库时
# 或：/opt/yunji/ops-venv/bin/python source/scripts/database_ops.py initialize
```

`initialize` 只接受不存在的新库，会先执行框架 schema，再按 V1…V22 应用业务迁移并写 SHA256。检查 `schema_history` 和脚本输出。重复部署同一包应使用 `migrate`；已应用 SQL 被修改、目标库有当前包未知的更高迁移时工具必须拒绝。固定使用 `/opt/yunji/ops-venv/bin/python`，避免误调系统解释器。

初始化成功后，设置新管理员口令：

```bash
/opt/yunji/ops-venv/bin/python source/scripts/database_ops.py bootstrap
```

两次隐藏输入至少 16 个字符的新口令。该操作替换 `user_id=1` 口令、停用其他框架初始账号、删除合成会话；它不会导入业务夹具。**仅首次建库执行 `bootstrap`，不能每次升级重跑**：实现会停用所有 `user_id != 1` 的工作人员，重复执行会影响后来新增账号。记录实际管理员账号名和口令保管位置，不在工单中写明口令。登录后台后按已批准的角色矩阵创建工作人员，不要把全部人设成超级管理员。

## 6. systemd 和 Nginx

复制 `source/deploy/systemd/yunji-api.service` 到 `/etc/systemd/system/yunji-api.service`。模板默认工作目录和 JAR 为 `/opt/yunji/current/backend/agri-admin.jar`；确认 `current` 已指向本次 release，应用用户是 `yunji`，`EnvironmentFile` 是 `/etc/yunji/api.env`。执行：

```bash
sudo ln -sfn "$REL" /opt/yunji/current
sudo systemctl daemon-reload
sudo systemctl enable yunji-api
sudo systemctl start yunji-api
sudo systemctl status yunji-api --no-pager
sudo journalctl -u yunji-api -n 100 --no-pager
```

日志出现 `YUNJI_APPLICATION_READY` 才进入 HTTP 验收。若启动保护拒绝，修正配置/管理员账号后重新启动，不要关闭 `ProductionGuard`。

复制 `source/deploy/nginx/yunji.conf`，替换 `server_name`、证书路径和实际 release 链接路径；模板已经拒绝 `/api/local`、合成客户登录、OpenAPI、Swagger、Actuator，并把 API 代理到 127.0.0.1:18088。先测试再重载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

确认公网只看到 80→443、H5 `/`、管理端 `/admin/` 和需要的 API；数据库、Redis、18088、私有附件目录不可从公网访问。不要把 Nginx 的 `alias` 指到附件根目录。

## 7. 隔离服务器验收清单

每项记录时间、操作者、域名、release、结果和日志路径：

| 检查 | 操作/预期 |
| --- | --- |
| 服务存活 | `systemctl is-active yunji-api`；journal 出现 `YUNJI_APPLICATION_READY`。 |
| HTTPS | `curl -fsS https://<试验域名>/api/v1/catalog/categories` 返回业务 JSON；HTTP 自动 308 到 HTTPS；证书主机名正确。 |
| 公开 H5 | 浏览器打开 `https://<试验域名>/`，静态资源无 404/混合内容，公开资讯/目录可见。 |
| 管理端 | 打开 `/admin/#/login`，用 `bootstrap` 后的管理员账号登录；验证码、后台页面和一次受权写操作通过。 |
| 本地入口封闭 | 外部请求 `/api/local/login-codes`、`/api/v1/auth/customer/local`、`/v3/api-docs`、`/swagger-ui`、`/actuator` 均为 404/拒绝。不要把合成 secret 带到服务器。 |
| 默认账号 | 框架其他初始账号停用；默认 `admin123` 不可用。 |
| 文件 | 用后台上传一个允许类型的合成文件，生成主体绑定票据，成功下载一次；第二次使用同一票据失败；越界/符号链接路径失败。 |
| 业务边界 | 用已批准工作人员执行资讯草稿→提交→审核→发布和一个客户公开读取；作者/审核员分离、旧版本公开指针和 409 版本冲突有记录。没有客户平台资源时客户动作可用本地研发证据，不要伪造服务器真实微信登录。 |
| 备份 | 停应用后完成数据库+附件配对备份，检查 manifest 和 SHA256。 |
| 监控 | 确认 systemd 崩溃重启、磁盘容量、MySQL/Redis 连通性、登录失败、迁移失败、通知 UNKNOWN 告警有人接收。 |

隔离服务器的客户真实微信登录、微信/企微通知、真机小程序体验版和正式公网切流必须标记 `BLOCKED_PLATFORM`，直到资源和 HTTPS 域名交付。不能用 H5 本地合成码替代。

## 8. 微信小程序交接

`artifacts/client-mp-weixin` 是构建产物，不是自动发布到微信的凭证。取得独立测试 AppID、开发者权限、API HTTPS 合法域名和测试账号后，由前端/平台人员在微信开发者工具导入该目录；把项目 AppID 设置为实际值，检查 `VITE_API_BASE_URL`/编译配置指向试验 HTTPS 域名，前端不放 AppSecret。若 AppID 在源码 `apps/client/src/manifest.json` 中变更，必须回仓库修改、重新 `npm run build:mp-weixin`、更新 manifest/哈希后再交包，不在开发者工具里留下不可追踪的唯一改动。

依次验收：开发者工具编译 → `uni.login` 换取 code → API 交换身份 → 新用户/旧用户会话 → 退出/过期 → 真机网络与文件下载 → 平台回调/订阅消息（若已实现）。没有平台资源时只确认构建产物存在和配置缺口，不得称为小程序上线。

## 9. 备份、升级、回滚和恢复

### 9.1 停写备份

数据库和附件必须是同一停写时点。先让 Nginx 进入维护页或停止 API，确认没有上传/写事务，再执行：

```bash
sudo systemctl stop yunji-api
set -a; . /etc/yunji/migration.env; set +a
/opt/yunji/ops-venv/bin/python source/scripts/database_ops.py backup \
  --application-stopped \
  --storage /var/lib/yunji/files \
  --destination /backup/yunji/$(date -u +%Y%m%dT%H%M%SZ)
```

`--application-stopped` 是操作者确认，不是工具对服务状态的证明。将备份目录加密、限制访问并保留异地副本；数据库、附件、配置密钥和平台凭据按公司保留策略分别保护。

### 9.2 正常升级

1. 审核新包 SHA256、源码指纹和 `release-gate.json`，确认不是过期包。
2. 停写并做配对备份；确认备份可读。
3. 将新 JAR、静态文件、迁移和文档放入新 `/opt/yunji/releases/<版本>`，不改旧 release。
4. 用独立迁移配置执行 `/opt/yunji/ops-venv/bin/python source/scripts/database_ops.py migrate`；检查日志。校验失败、未知更高版本或任何 DDL 异常都暂停发布。
5. 在维护窗口、API 已停止的前提下，将 `current` 切换为新 release，再通过 systemd 启动新 JAR；systemd 模板始终读取 `current/backend/agri-admin.jar`。执行第 7 节 HTTP、权限、文件和关键业务检查，全部通过后开放入口并重载 Nginx。保留旧 release；不要在公开入口仍接收请求时切换前后端。

### 9.3 失败回滚

先停止新版本并保留日志、数据库状态、附件目录和请求时间线。只有确认旧程序兼容当前 schema，才可只切回旧 JAR；否则不能把程序切回旧版本后继续读新 schema。标准恢复是把备份恢复到**新数据库名和新附件目录**，验证后同时切换对应版本和配置：

```bash
set -a; . /etc/yunji/migration.env; set +a
export YUNJI_MIGRATION_DATABASE='yunji_restored_<新批次>'
/opt/yunji/ops-venv/bin/python source/scripts/database_ops.py restore \
  --source '/backup/yunji/<timestamp>' \
  --storage /var/lib/yunji/files-restored
```

`YUNJI_MIGRATION_DATABASE` 必须替换为一个**不存在**的新库名，并由 DBA 为恢复身份授予建库权限。恢复工具拒绝覆盖现有库或附件目录，并逐项校验 manifest。恢复后修改受限 API 配置指向新库/新附件，切回与备份 schema 兼容的 release，启动服务，验收登录、公开资讯、私有文件和已具备资源的客户路径；平台受限项仍单独记录。原库和原附件先保留，待负责人批准再处理。

## 10. 故障处理顺序

1. 记录发生时间、release、配置文件哈希、请求路径、用户主体和是否有写入；不在日志中复制 token、密码、微信 code 或附件内容。
2. `systemctl status`、`journalctl -u yunji-api`、Nginx error/access log、MySQL/Redis 日志按时间对齐；先判断是服务启动保护、网络、数据库、权限、文件还是平台供应商。
3. 看到 `schema`/checksum 错误时停止迁移，保全数据库与日志；不要编辑旧迁移或强行删除 `schema_history`。
4. 看到 401/403/404/409/422 时，用实际主体和请求哈希复现；409 重新读取并确认 `lockVersion`，不要重复生成新幂等键覆盖结果。
5. 文件失败时检查附件目录权限、磁盘、符号链接、数据库元数据 SHA256 和票据是否已消费；不要直接从旧静态目录补文件。
6. 微信/企微失败时确认 AppID、域名、回调验签和供应商状态；没有资源时保持 `PLATFORM_PENDING`，不要打开 local gateway 代替。

## 2026-10-21 原型改版部署增量

本轮无新增数据库迁移、环境变量、运行端口、平台密钥或依赖版本变更，继续以 V1～V22 增量迁移校验和及已有 Docker 配置交接。必须同时构建并发布新后端和新 C 端：旧后端不能提供多关键词、关注标签关系和规则对象过滤。

1. 本轮目前只在本地候选分支；等待仓库所有者明确推送后，接收团队核对远端分支与完整 SHA，不把旧分支当本轮。
2. 按既有操作书备份、校验迁移历史、使用独立测试配置；构建 JAR、admin Web、client H5 与 mp-weixin，保留各自哈希。
3. H5 hash 路由不新增网关前缀；小程序仅发布 client 的 mp-weixin 构建产物，不能导入静态 HTML 原型或把 H5 当小程序包。
4. 烟测公开首页、资讯详情与原文、学校组织筛选、个人中心、登录取消、信息盒子摘要/已读/隐藏；使用独立测试身份验证关注分组、批量标签关注、三视图提醒和既有活动/申报/文件下载。
5. 平台未接入时保持明确的待接入状态，不为满足 UI 人工补真实授权额度、不通过“已扫码”按钮绑定账号。
6. 回退按整版后端与 C 端配对回退，本轮不回滚任何已安装数据库历史。新接口是兼容扩展，旧客户端仍可调用原字段；回退后端前应先回退依赖新接口的客户端。
7. Linux amd64 Docker、HTTPS、域名白名单、真实平台及安全门禁按既有接力清单实测。Windows H5 本地通过不等于这些门禁通过。
