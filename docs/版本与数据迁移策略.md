## Git 版本管理

本工程是独立 Git 仓库，仓库根目录是 `yunji-platform`。它只管理新工程源代码、数据库迁移、部署模板、验收脚本和审计文档；`yangben` 不在仓库内，也不会作为 Git 子模块、依赖或代码来源。

当前仓库使用 `feature/brand-yunji` 作为本轮交接分支，已跟踪公司私有远程仓库 `qianyue303jiaojie/yunji-platform`。本轮提交不会自动合并 `main`：

```bash
git fetch origin
git switch feature/brand-yunji
git pull --ff-only origin feature/brand-yunji
```

日常开发使用短分支和合并请求：

```text
main                  可交付基线
feature/<功能>        单一功能开发
fix/<问题>            缺陷修复
release/<版本>        发布候选冻结
```

每次修改必须包含代码、数据库迁移、接口契约/前端模型、测试和文档中受影响的部分。提交前依次执行构建、接口回环、浏览器回环、运维演练、来源核查和门禁报告；通过后打版本标签，例如 `v0.1.0-rc.1`。正式版本使用 `vMAJOR.MINOR.PATCH`。

## 版本更新规则

1. 只新增迁移文件，例如 `V20__meaningful_name.sql`；已应用的 `V1`–`V19` 不改名、不改内容、不删除。
2. 先在新空库和数据副本上执行迁移，再做构建和完整回环；迁移脚本会用 SHA256 校验历史文件，发现已应用文件被改写会拒绝继续。
3. 发布包包含同一版本的后端 JAR、管理端静态文件、C 端 H5、小程序构建产物和迁移目录。服务器上切换不可变 release 目录，不直接编辑运行中的文件。
4. 生产升级前停写、备份、执行迁移、启动新版本并验收；失败时保留日志，按备份恢复到新库和新附件目录。禁止把未知 schema 降级当成回滚。
5. 交付包的 `manifest.json` 和 SHA256 是接收团队验收依据；服务器临时修改必须回写工程、重新测试、重新打包。

## 旧项目数据迁移

可以迁移“数据”，但当前工程没有把旧库直接导入作为完成条件，也没有自动兼容旧表的导入器。这是有意的：旧项目代码、旧接口、旧表结构和旧部署脚本都不进入新系统。

数据迁移应作为一次独立、可审计的迁移项目完成：

1. 从旧系统取得只读导出或数据库备份，并记录来源库版本、导出时间、表清单、附件清单和 SHA256。导出文件放在工程外的受限目录，不提交 Git。
2. 在 staging 建立原始行快照、来源表名、原始主键、批次号和行哈希；原始快照只用于追溯，不直接被新业务读取。
3. 按新领域模型做显式映射：组织/用户、目录、内容及版本、互动关系、活动、评审、资料包、附件和审计分别处理。每个字段写明来源、转换、可空规则、默认值和拒绝原因。
4. 旧主键和新主键通过 `migration_id_map` 记录；批次重跑必须幂等。无法确定归属、状态、时间或组织的数据进入隔离表，不能静默猜测。
5. 密码、微信/企微身份、手机号等敏感身份不按昵称或手机号盲目合并。微信身份只有在 AppID 归属和绑定证据齐全后才能迁移；否则让用户重新绑定。
6. 旧附件必须重新扫描类型、大小、哈希和路径，写入新私有存储；不得把旧静态目录直接映射到 Nginx，也不得把旧路径写入新下载票据。
7. 先做 dry-run 报告，再导入一份脱敏副本，执行数量、唯一性、引用完整性、版本状态、权限隔离和附件哈希核对。业务负责人确认报告后，才安排正式停写窗口。

当前状态：新库初始化、V1–V19 schema 迁移、备份恢复已经完成；旧数据导入脚本和字段映射尚未开始，因为尚未收到正式旧库导出、数据字典、附件清单和保留范围。拿到这些资料后可以只迁数据，不引入旧项目代码。

## 明确禁止

- 不复制旧项目 Java、Vue/uni-app、SQL 业务表、请求封装或部署脚本。
- 不把旧 SQL 初始化文件直接在新库执行。
- 不用旧 ID 直接当新系统身份主键。
- 不在没有映射、校验和回滚方案时连接正式旧库。
